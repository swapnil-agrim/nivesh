## Decisions recorded in ADR-0013 (owner decisions OD-n, deferrals Xn)
- **OD-1 last_close basis (#94/X4)**: `ledger_entry.last_close` is the **split-adjusted close as of the issue date, for display only**. Scoring never divides by it: it re-reads the issue-date bar and the horizon-end bar from the **same current series** (`load_bars`, split-adjusted), so a split after issue cannot corrupt a return. Same for the benchmark. Dividends are not applied (price return, as ADR-0008 for engines); this is labelled `basis = split_adjusted_price` in every score row and output, and total-return/TRI is deferred (X2). The benchmark level stored at issue is likewise informational.
- **OD-2 Issue date**: new `ledger_entry.as_of` (run day) and `price_date` (date of the bar `last_close` came from). Scoring entry bar = the bar dated `price_date` when present (the bar `last_close` came from), NOT the as_of snap, so a bar dated as_of that did not exist at run time is never the entry. Old rows have neither; the legacy fallback is keyed on **`as_of IS NULL`** (not on `price_date`): `as_of` = IST date of `created_at`, entry bar = last bar on or before it within 5 days. A new row with `as_of` set but `price_date IS NULL` (no bars at issue) is NOT legacy: it never borrows a later bar and stays pending, then insufficient after the grace window. Documented, covered by tests. Backfill by UPDATE is impossible by design. `decided_at`/`created_at` are record time, not trade date (ADR note; calendar-year edge for #87): `nivesh decide` takes optional `--on DATE` (trade date, stored in `ledger_decision.on_date`, default = IST record date) and OD-10 buckets by `on_date`.
- **OD-3 Horizons** 1/4/13/26/52 weeks. Target date = `as_of + 7*w` days. "Sessions" are the stored bar dates of the security (no holiday calendar dependency, so no `CalendarUnknown`): entry = bar at `price_date` when present, else (legacy rows only) the last bar on or before `as_of` (within 5 days, else INSUFFICIENT), end = last bar on or before target. **Pending** (no row written) until the latest stored bar date of both security and benchmark is >= target; never forward-filled.
- **OD-4 Rules**: costs (config, percent round trip): IN 0.25, US 0.10. `BUY/ACCUMULATE`: `call_excess = ret - bench - cost`, hit = call_excess > 0. `SELL/TRIM/AVOID`: do-nothing comparison, `call_excess = bench - ret`, hit = call_excess > 0 (no cost; the owner's alternative is to hold). Raw `excess = ret - bench` is stored for display only; **all mean/median/worst/calibration aggregation uses `call_excess`**, one sign convention across verdicts. `HOLD`: scored (ret, excess stored) but `hit = None` and `call_excess = None`: excluded from hit rate AND from mean/median/worst (counted in calls and scored). `INSUFFICIENT_DATA` verdict: one row per horizon with status `insufficient_data`, counted in "calls", excluded from "scored". **Staleness rule**: `score_call` takes explicit `today` and `stale_days`. If one leg has a bar >= target but the other leg's last bar is older than `scoring.stale_days` (default 7) before target, or that leg has no bars, the row is `insufficient_data` (counted, not scored); otherwise pending. An `insufficient_data` row is written only when `today >= target + stale_days` (grace for late data); inside the grace window the call stays pending. The stale test uses **the last bar on or before target** of each leg (older than `stale_days` before target, or none = insufficient; a bar after target does not rescue it, no forward-fill). `insufficient_data` is **not permanent**: the unique index is partial (E1), so a later `scored` row for the same (entry, horizon, version) is appended after a data backfill while `scored` rows stay append-only and are never superseded by insufficient rows. Readers take the latest row per (entry, horizon, version), preferring `scored`. `SCORE_VERSION` bump stays for rule changes (R-4).
- **OD-5 Benchmark**: `scoring.benchmarks` market -> index symbol, defaulting to `analysis.ta.benchmarks`; basis note "price index, not TRI" on every output until the owner loads and configures a TRI symbol (X2).
- **OD-6 Scorecard**: bucket < 20 scored calls is "not enough data" (`scoring.min_bucket`). **Unit of count = CALL (distinct surviving entry), never score row.** One call yields up to 5 score rows (one per horizon); the floors (20 here, 40 in OD-7) and the bootstrap count distinct calls. All dimensions except `horizon` aggregate at one **primary horizon** (`scoring.primary_horizon_weeks`, default 13, one of the five); the `horizon` dimension shows each horizon_weeks as its own bucket (a call is in exactly one row per bucket), so rows of one call are never pooled as independent. Dimensions: verdict, horizon, market, conviction, command (from `run.command`), and **system vs acted**. **Decision semantics (one rule for E4, E18, OD-10, OD-6)**: only effective rows count (a row that is the target of a later `corrects_id` is ignored; the correction replaces it); `acted`/`partial` rows SUM; a later `skipped` does NOT cancel an earlier `acted` (only `--corrects ID` undoes it). Acted = any effective `acted`/`partial` row; none or only `skipped` = system only. **Dedupe (E10)**: key (security_id, as_of date, verdict, horizon) with survivor = latest id; plus per-(security, verdict) overlap-window dedupe: later repeats of the same verdict within 7*weeks days of the surviving call are dropped (earliest survives), so daily/weekly holding reviews do not stack; dropped counts are shown in output and ADR. Decisions on a dropped entry map to its survivor.
- **OD-7 Calibration**: >= 40 scored calls (`scoring.calibration_min`) over hit-eligible **calls at the primary horizon** (calls, not rows); per conviction bucket hit rate and mean excess with a seeded bootstrap 90 percent CI (`resamples` default 1000, `resample_seed` default 20260101, integer xorshift). HOLD is excluded from hit-eligibility and from mean/median/worst (still counted in `calls`). Monotonic means non-strict `high >= medium >= low` on hit rate; verdict text `monotonic`, `not monotonic`, or `inconclusive` (adjacent CIs overlap). Below 40: "not enough data".
- **OD-8 Look-ahead guard**: `evaluation.model_cutoffs` (model id -> date) in config; `assert_out_of_sample(eval_start, model_id, cutoffs)` refuses unless `eval_start > cutoff`; unknown model or empty map refuses. Used by the golden harness for any case/run tagged `historical` and exposed for later callers.
- **OD-9 Golden gate**: `tests/eval/baseline.json` committed (pass rate 1); a run blocks release when `baseline - pass_rate > 5pp` **or any `safety` case fails**; baseline file absent = report only.
- **OD-10 Turnover (#87)**: year-to-date = calendar year (X5 for Indian FY), sum over effective (OD-6 semantics) `ledger_decision` rows with decision `acted`/`partial`, bucketed by `on_date` (trade date), on entries whose verdict is `SELL`/`TRIM` (HoldingReview `EXIT` maps to `SELL`), of `qty * price` (USD converted with `settings.usd_inr`, Decimal). The cap used by `propose_moves` becomes `max(cap% * total - ytd_sold_inr, 0)`. Documented approximation: divided by today's portfolio total (no year-start NAV store).
- **OD-11 HoldingReview rows**: `ADD -> ACCUMULATE`, `EXIT -> SELL`, `TRIM`/`HOLD` as is, `REVIEW` writes no row. Horizon from the active thesis, conviction = confidence, review date = thesis review date, `source = 'holding_review'`, `as_of` = review day and `price_date` = date of the holding price used in the review (not the legacy fallback; no price date -> NULL, row stays insufficient), input hash = sha256 of the saved review JSON, no weight/zone.
- Deferrals **X1..X6** map to the follow-up table.
