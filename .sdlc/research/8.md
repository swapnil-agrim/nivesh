# Research: E5 Mutual fund intelligence (ST-5.1 to ST-5.7)
**Goal**: swapnil-agrim/nivesh#8 · **Lane**: large (upper end; recommend 3 slices) · **Date**: 2026-10-10

## Goal in one paragraph
Judge every Indian mutual fund the owner holds on cost, consistency, risk, overlap and forward valuation, entirely in deterministic code: an AMFI-code NAV adapter (MFapi.in primary, AMFI NAVAll fallback) with incremental history and gap flags (ST-5.1); scheme metadata, regular-to-direct twin mapping and TER cost difference (ST-5.2); 12 months of monthly fund holdings mapped through the security master (ST-5.3); a rolling-return and risk analytics engine plus portfolio P/E and P/B vs own 3y history (ST-5.4); pairwise overlap and look-through exposure (ST-5.5); a fund doctor with five actions (ST-5.6); and candidate discovery (ST-5.7). Source: PID sec 21 (lines 893-956), 15.3 (506-516), 12 (MF NAV and MF metadata rows), 13 data model (FundMeta, FundHolding in DuckDB), FR-20 (235), BR-12 (190), design/1.md row "E5 ... depends on 3, 4" (line 74). Checked against `.sdlc/work/8` (HEAD cdf64c1 = E1+E13+E2+E4+E3 merged). Fixtures only, no network, read-only, no new heavy dependency (numpy/pandas/scipy are NOT project deps in `pyproject.toml`; stay Decimal-only like `returns.py`).

## Decisions the plan must make (with recommendations)
- D-A NAV storage. Recommend a DuckDB `nav_point(security_id, date, nav DECIMAL(18,4), source, PRIMARY KEY (security_id, date, source))`, keyed by the E4 `security.id` for MFs (symbol `<ISIN>`, exchange `AMFI`) rather than raw amfi_code, so `fund_holding`, holdings and NAV all join through the master. Incremental: request only dates after `last_nav_date`; MFapi returns the full history per call so filter client-side and upsert; AMFI NAVAll gives only the latest day per scheme, so as fallback it appends one point per run. Source precedence: MFapi over AMFI on the same date; disagreement beyond tolerance becomes a flag (like `cross_check` in E4).
- D-B Gap definition. "More than 5 trading days": recommend config `mf.nav_gap_days: 5` and a gap = consecutive missing weekday-or-AMFI-observed days; compute from the union of dates across all stored schemes (a date any fund has a NAV is a business day) with a weekday fallback minus configured holidays; avoids `CalendarUnknown` for historical years. Gaps returned as ranges in the ingest report and stored flag, not silently filled.
- D-C Numeric type. Recommend Decimal for NAV and weights; rolling-return and ratio math in Decimal with explicit rounding (`quantize`) at the output boundary. Std dev and annualisation need a square root: use `Decimal.sqrt()` (no numpy). Determinism test: same input twice gives byte-identical output. Fixture with known answers: hand-computed tiny series (e.g. 12-24 points scaled window parameters) so tests assert exact values; the 3y/5y windows are parameters (`window_days`) so the fixture can use short windows plus one test at real window sizes on a synthetic series.
- D-D Rolling definitions (document in ADR): window in calendar days (3y = 1095, 5y = 1826 or by year offset), daily step, annualised CAGR per window; excess = fund window return minus benchmark window return; "beating %" = share of windows with excess > 0; downside capture = mean fund return over benchmark-down periods / mean benchmark return over same periods (monthly or daily returns, document); Sortino with owner-set MAR (default 0 or `risk_free` from `usdinr`-style macro if available; default 0, parameterised); max drawdown on NAV. Mismatched NAV and benchmark dates: align on common dates, report coverage.
- D-E Direct-twin resolution. Recommend deterministic matching on scheme-name normalisation: strip "Direct", "Regular", "Plan", option words, "- ", then same AMC + same normalised name + plan=direct + same option; AMFI direct-plan names carry "Direct". Candidates > 1 returns "ambiguous" with the list, never a guess. Cost: `(ter_regular - ter_direct)` in % and `x current_value` per year in INR using current value from consolidated `Row.value_inr`.
- D-F Candidate universe for ST-5.7. Recommend: candidates are schemes with stored NAV + `fund_meta` + `fund_holding` in the same SEBI category; the user populates the universe via `nivesh mf nav --category ...` (or a configured watch-list `mf.universe`). Fixture-only in tests. Ranking: documented weighted rank-sum of consistency, downside capture, TER, valuation, with weights in config; tie-break deterministic (amfi_code).
- D-G BR-12 guard. Recommend the doctor takes explicit fields and a `ReasonCode` enum; a `trailing_1y` metric is accepted as input only for display, and a unit test (`fund with top 1y return, poor consistency`) asserts the action's reasons include at least one non-1y metric and that removing 1y from the inputs never changes the action. Add a property-style test over varied 1y values.
- D-H Fund doctor precedence. Recommend ordered rules: (1) regular plan with direct twin and positive TER gap -> SWITCH-TO-DIRECT; (2) overlap above threshold with another owned fund of same category -> CONSOLIDATE; (3) consistency below threshold or drawdown/downside capture bad -> REPLACE when a candidate exists, else REVIEW; (4) manager change or drift or valuation stretch -> REVIEW; else KEEP. Thresholds from config. Every action carries `reasons: list[{code, metric, value, threshold}]`. SWITCH/REPLACE results embed `exit_load` and `tax_impact` blocks before the action field order in the payload.
- D-I Ingest and MCP surface. Recommend CLI only this goal (`nivesh mf ...`); no new MCP server; no `.mcp.json`/settings.json change. Cheaper and avoids the tool-count test churn. Flag in ADR that ST-7.5 will expose these via `engine.*`.
- D-J Monthly holdings history of 12 months. Recommend schema keyed (amfi/security_id, month_end, isin, weight_pct, source) append-only per month; ingest takes the latest N months the source offers; AC "at least 12 months" met by fixtures with 12 months for one fund, and a coverage report (`months_stored`) so shortfalls are visible. Unmapped weight = sum of weights of ISINs with no master row, reported per fund-month (cash/derivative/non-equity lines kept as their own bucket).

## Redaction-safe field names (ADR-0004)
Use `amfi_code`, `scheme_name`, `category`, `plan`, `option`, `expense_ratio`, `aum`, `benchmark`, `manager`, `manager_since`, `nav`, `weight_pct`, `overlap_pct`, `exposure_inr`, `exposure_pct`, `as_of`, `source`. Avoid in outputs/fixtures/config any key containing `token`, `secret`, `password`, `authorization`, `cookie`, `folio`, `aadhaar`, `apikey` or the underscore parts `pan`, `account`, `acct`, `key`, `email`, `phone`, `mobile`, `address`, `dp`, `client`. Hazards: a field called `manager` is fine, `fund_manager_email` is not. Folio numbers must never enter MF tables (CAS layer drops them; MF engine reads `holder_ref` hashes only). `redact.py` masks any 9-18 digit run: NAV history rows with long unbroken digits are not at risk, but AUM strings (e.g. crore values) and "scheme code" lists could match; emit JSON numbers, keep Decimal strings short, and assert on real values in tests. No real holdings or PII in fixtures: use the `Example Mutual Fund` style synthetic names (as in `amfi_navall.txt`) and invented ISIN-shaped codes (`INF000A01011`).

## Issue #53 (XIRR bracket)
`nivesh_engine/returns.py:20` `LOW, HIGH = Decimal("-0.999999"), Decimal(100)`; `xirr` bisects within [LOW, HIGH] after a sign check (`:47-50`). HIGH=100 means annualised 10000%, so a short high-gain hold (e.g. +100% in 30 days, annualised far above that) fails the `(f_lo > 0) == (f_hi > 0)` test and returns None. The issue also asks for an all-negative-flows test returning None with reason. Status: E5 does not require XIRR in any ST-5.x criterion, but ST-5.6 "tax impact from lots" and per-fund holding period may reuse `holding_days`/`is_long_term` and a lot-XIRR display could reuse `xirr`. Recommendation: if any E5 code calls `xirr` or `lot_report`, fix #53 in the same PR (expand bracket, e.g. widen HIGH or grow the upper bound geometrically until a sign change, cap iterations; add tests: +100% in 30 days, all-negative flows -> None with reason, no-sign-change); otherwise leave #53 out of scope and do not touch `returns.py` (it stays a separate P1 follow-up). Prefer the first only if lot XIRR for MFs is actually shown; holding days plus FIFO gain need no XIRR. Note `xirr` returns None, not a reason; the "with reason" part is produced by `lot_report` (`reason_usd`).

- Hidden coupling: look-through sector needs `security.sector`, populated only where the NSE/BSE/SEC masters supply it; report coverage.

## Lane rationale
Large, upper end. Roughly 23 sites: two to three new stores/tables, two new adapters, 7 new engine modules, config block, CLI, ADR, ~30 new test files, one DuckDB migration; each AC is its own testable unit (seven stories, PID sizes M,S;M,M;M,M;M,M;M,S;M,M;S,S). No new dependency, no new MCP server, no network. Risk is in correctness of financial math and in unverified wire formats, not in structural change. Too big for a single reviewable plan: recommend 3 slices (sequenced; each ends `make check` green, each its own PR if the loop splits):
1. Data layer: ST-5.1 (NAV adapters + store + incremental + gap), ST-5.2 (metadata + direct twin + TER cost), ST-5.3 (monthly holdings + ISIN mapping + unmapped weight); migration `duck/0003_mf.sql`, `mf_store`, `by_amfi_code` lookup, config `mf` block, ADR-0007, CLI `nivesh mf nav|meta|holdings`.
2. Analytics: ST-5.4 (rolling, risk, valuation lens), ST-5.5 (overlap matrix, look-through); pure engine modules, known-answer fixtures.
3. Decisions: ST-5.6 (fund doctor, exit-load/tax-impact, BR-12 test, deferrals recorded), ST-5.7 (discovery); CLI `nivesh mf doctor|discover`; fix #53 only if XIRR gets used.
Review skills to flag: `/sigma-migration-check` (duck 0003), `/sigma-contract-check` (config schema, Holding/Txn consumers if touched), `/sigma-security-review` (external data parsing, untrusted fund metadata strings feeding agents; wrap with `untrusted` if any text reaches an agent).

## Risks
- R-1 Trailing-return leakage into the doctor (BR-12/ST-5.6): guard with D-G tests; reasons must cite consistency/cost/overlap metrics.
- R-2 Silent zeros: missing TER, missing benchmark, no exit-load row, unmapped weight, absent history must give "unavailable"/None with a reason, never 0 (house rule since E3 R-1).
- R-3 Non-determinism: Decimal context, sort ties, dict ordering, benchmark alignment; add byte-identical rerun test.
- R-4 Scope blow-up from the valuation lens (needs per-holding P/E and P/B history). Mitigate by computing from stored fundamentals/bars only, reporting coverage %, and allowing "unavailable" with the rest of ST-5.4 shipping; record partial in PR.
- R-5 Unverified wire formats produce wrong parsing that fixtures cannot catch. Mitigate with strict `DataQualityError` validation (date format, NAV > 0, weights sum <= ~101%) and an explicit "unverified" note in ADR; follow-up live check.
- R-6 Regular/direct twin mismatch (ambiguous names) producing wrong "switch" advice: ambiguity returns explicit "ambiguous", plus test with near-duplicate names.
- R-7 Look-through double counting: a fund that holds another fund or ETF, cash lines, derivatives; consolidated Row for a direct-equity ISIN plus the same ISIN inside funds must sum; unmapped bucket reported.
- R-8 Corporate-action and IDCW effects on NAV series: IDCW options distort returns (NAV drops on payout). Use growth-option ISIN/code for analytics; flag IDCW schemes "returns not comparable" instead of computing.
- R-9 Secret-scanner/PII/redaction hazards (sections above); gitleaks in CI.
- R-10 Coverage gate 85% on `nivesh_engine`/`nivesh_adapters`; new modules must be fully tested, including edge branches (short series, empty window, benchmark missing).
- R-11 Calendar: windows and gap logic crossing NSE years absent from config (TD-4).
- R-12 Test fixtures size: 3y/5y daily windows need 1100+/1800+ points; generate synthetic series deterministically in `tests/mf_fx.py` (formula-based) instead of committing large files, and keep a small hand-checkable fixture for exact-answer tests.
- R-13 Agent-facing text: scheme names/manager strings are untrusted external text; if surfaced to an agent later, wrap via `nivesh_agents/untrusted.py`.

## Verdict summary
- Lane: large (upper end); recommend 3 slices (data layer ST-5.1/5.2/5.3; analytics ST-5.4/5.5; decisions ST-5.6/5.7).
- Hard blockers: none. ST-2.8 and ST-4.8 are built; ST-7.5 is not (defer the agent/`/review-funds`, ship deterministic doctor).
- Key risks: BR-12 (1y return never sole reason), silent zeros, deterministic Decimal math with sqrt/rounding, unverified MFapi/MFData formats, valuation lens needing 36 months of data, calendar gaps, secret-scanner/redaction hazards.
- Recommended deferrals: ST-7.5 agent and MCP exposure, category/TRI benchmarks, live source verification, exit-load scraping (owner-set config), detailed India MF tax, #53 unless XIRR is reused.
