# Research: E2 India holdings ingestion (ST-2.1 to ST-2.9)
**Goal**: swapnil-agrim/nivesh#5 · **Lane**: large · **Date**: 2026-10-09

## Goal in one paragraph
Build the India holdings pipeline on the E1/E13 base: InvestRight runbook and daily login, a read-only InvestRight client, normalisation to the standard holding schema, casparser-based CDSL/NSDL and CAMS/KFintech CAS ingestion (PII stays in the parser layer, folios hashed), CSV import with broker presets, consolidation with precedence plus reconciliation, and a read-only `nivesh-holdings` MCP server. Source: PID lines 661-752 (sec 18); FR-1/2/3/4/6/7/8/9, NFR-1/3/5/6, BR-13, CR-2, OBJ-1 (PID lines 74, 191, 206-214, 272-277, 308); data model PID lines 354-366. The seed `investright-mcp` is absent (design PC-1), so everything is written from the spec, fixtures only (no network, no real holdings, no PII). One upstream is unbuilt: ST-4.8 security master (ST-2.4 depends on it), so identifier resolution must go behind an interface.

- Unverified: Zerodha/Groww/Upstox export column layouts.
- Constraint: NFR-1/CR-1 no write methods anywhere; adapter must not even define helpers whose names contain write verbs; `write_methods` is a name check (`place|modify|cancel|transfer|order|buy|sell|delete|withdraw`). An `exchange_token`-style method name is fine; `order_book` would fail.

- Constraint: Decimal for quantities/prices/values (casparser uses Decimal); JSON-serialise as strings or floats consistently; mind `redact_json` masking 9+ digit numeric strings.

## Lane rationale
Large. Footprint: about 20 sites across 6 packages (adapters, engine, core, mcp, cli, agents wiring) plus config, docs, templates, CI/image; 1 new third-party dependency with native wheel and a 47 MB data package (NFR-6); 2 new persisted shapes (migration 0003 holding snapshot and transaction tables, 0600 token file) and 1 changed config schema; 1 new MCP server (7 tools) crossing the NFR-3 redaction middleware, whose key-name masking collides with natural field names; 9 stories where one upstream (ST-4.8) is missing and the integration surface (InvestRight wire format, real CAS PDFs, broker CSV layouts) is unverifiable offline. Recommend slicing:
- (A) ST-2.1 + 2.2 + 2.3: runbook, IST/token store, login flow, read-only InvestRight client with errors and introspection test (BR-2, 10, 11, 12, 13, 14, 16).
- (B) ST-2.4 + migration 0003 + holding schema/resolver interface (BR-4, 5, 6 naming decision).
- (C) ST-2.5 + 2.6: add `casparser` pin, parser-layer boundary, ingest report, folio hash, redaction test, `nivesh ingest`.
- (D) ST-2.7: CSV template, validation with line numbers, three presets.
- (E) ST-2.8: consolidation, precedence, reconciliation, coverage report in `nivesh_engine`.
- (F) ST-2.9: `nivesh-holdings` server, registry/.mcp.json/settings entries, e2e through `fastmcp.Client` with redaction.
Order A, B, C, D, E, F (E needs B/C/D; F needs E).

Defer explicitly (with follow-up issues): ST-4.8 security master build (nightly NSE/BSE/AMFI loads, fuzzy names, renamed ISIN mapping); real casparser PDF round-trip with actual CDSL/NSDL/CAMS/KFintech statements (needs owner PDFs, no PII fixtures); live HDFC verification (login, OTP, holdings, LTP, static IP, error 60014 wording); US holdings (E3); FX conversion; SSH tunnel for daily login on a VM (E13 F4 remainder); verification of Zerodha/Groww/Upstox layouts against real exports; a holdings TTL entry in cache config if live-session caching is wanted.
